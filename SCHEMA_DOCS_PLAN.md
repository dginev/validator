# Schema Documentation: Design Plan

A plan for the scholarly LaTeXML HTML5 schema docs generated by
`tools/generate-scholarly-schema-docs`. Current output is LaTeXML's
HTML5 with a rustdoc-derived stylesheet; this plan covers what to
change, what to leave, and what to refuse.

## Reader

One reader profile: a developer who needs to locate a definition by
name and read its content model. Discovery and learning workflows are
real but rare and don't reshape the design.

## What's actually wrong with the current docs

1. **Content models render as one-line walls of comma-separated
   links.** `(A , (B | C)? , D*)` looks the same as `(A | B | C | D)`.
   The reader has to parse operators in linear order to recover
   structure.
2. **Pattern / Element / Attribute / Value identifiers are
   typographically indistinguishable.** The reader has to read the
   kicker label to know what kind of thing they're looking at.
3. **Anchors are auto-generated `I1.ix1`-style ids** — meaningless in
   URLs, no help for sharing or bookmarking.
4. **"Used by" lists are visually buried** (trailing footnote
   position) but are half the navigation graph.

Everything else (sidebar, breadcrumb, header, dark theme) already
works.

## What to build

### 1. Content-model renderer — priority

Pretty-print the structural expression behind every `Content:` line:

- One operand per line for sequences/choices longer than ~4 tokens.
- Indented continuation for nested groups.
- Operators (`,` `|` `&` `*` `?` `+`) coloured distinctly so the eye
  can skip them.
- Quantifiers (`?`/`*`/`+`) as superscripts attached to their operand.

Implementation: post-process the existing flat HTML in Python (same
pipeline as `inject-module-sidebar.py`). Migrate to a LaTeXML-emission
change once the visual design has stabilised.

### 2. Definition cards

Each Pattern / Element / Attribute becomes a self-contained card with:

- A small uppercase kind chip (`PATTERN`, `ELEMENT`, `ATTRIBUTE`).
- A stable semantic anchor (`#schema.<name>` instead of `I1.ix1`) —
  LaTeXML already emits an `<a name="schema.X">` inside each
  description; promote it onto the parent `<dt>` during
  post-processing.
- A `§` permalink button visible on hover.
- Content model + Used-by + (collapsed) RNC source inside.

### 3. Kind-aware typography

| Kind | Visual treatment |
|---|---|
| Pattern | code font, schema-blue link, dotted underline |
| Element | code font, **bolder** weight, green link, namespace prefix dimmed |
| Attribute | code font, leading `@` glyph, amber link |
| Value | code font, surrounding `"…"` quotes, purple |

Color is never the sole carrier of meaning — weight and prefix glyphs
also distinguish kinds.

### 4. Group definitions by kind within each module

Today they appear in source-declaration order. Group as
**Patterns → Elements → Attributes**, alphabetised within each group.

### 5. Module narratives

One curated paragraph (≤3 sentences) per module, in
`tools/module-summaries.toml`. The injector prepends it to the
module's content area before the definitions. Cap at 2-3 sentences so
drift from the schema is trivially fixed.

## Acceptance criteria

Concrete and falsifiable; the docs are done when these hold.

1. A reader can read any content model and identify the
   sequence/choice/repetition structure at a glance, without parsing
   operator characters in linear order.
2. A reader can locate any definition by name in ≤5 seconds — sidebar
   scroll plus browser Ctrl-F, no search engine.
3. Following a cross-reference is one click; the back-button restores
   scroll position.
4. The kind of every definition is visible without reading the label
   (kind chip + typographic distinction).
5. Dark theme passes WCAG AA on all body text.

## Things we are NOT doing

- Client-side search. (Browser Ctrl-F + alphabetised sidebar handle
  ~430 definitions.)
- Hover popovers / inline previews.
- Per-element / per-pattern pages.
- Anatomy or dependency-graph visualisations.
- Hand-curated semantic categories beyond the existing module
  groupings.
- A "Reading the schema" tutorial.
- Examples / corpus snippets.
- No-JS fallback for features we aren't building.

Each is defensible to add later. None makes the difference between
functional and non-functional today.

## Risks

- **Post-processor brittleness.** Regex parsing of LaTeXML's HTML
  output works today but breaks silently if emission shifts. Mitigate
  by tightening regexes with structural assertions; migrate to a
  LaTeXML emission change (custom `\patterndef` body emitting a
  structured `ltx:patternexpr` element) once the visual design has
  stabilised.
- **Curation drift.** Module summaries are hand-written. Cap each at
  2-3 sentences so drift is cheap to fix.
- **Local override vs upstream change.** Prefer overriding LaTeXML
  commands in our `schema-doc.tex` over editing
  `LaTeXML/Common/Model/RelaxNG.pm`. Send accepted improvements
  upstream once they've proven valuable here.

## Phase 1, in order

1. Structural content-model renderer (the single highest-leverage
   change; everything else is decoration around it).
2. Definition cards with kind chips, semantic anchors,
   permalink-on-hover.
3. Group by kind within module, alphabetised.
4. Module narratives loaded from `tools/module-summaries.toml`.
5. Acceptance check against the five criteria above. Stop here unless
   one fails.

Phase 2 is conditional: revisit only if (1)–(5) leave a felt
navigation pain that the visual changes don't address.
